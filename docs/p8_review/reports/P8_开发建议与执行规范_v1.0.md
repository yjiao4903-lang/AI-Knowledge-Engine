# 0. 执行摘要

## 0.1 当前阶段定性

当前项目已经基本完成 P7 的核心目标：**完成全量知识语料入库并建立一致性可核验的数据底座**。

上游报告确认：

- 全库已达到 **3,566 篇文档 / 296,385 个 chunk**
- `chunks = fts_terms = fts_trigram = qdrant_points = 296,385`
- `consistent = true`
- Qdrant 向量缺口已由 1,266 清零
- 本轮 473 篇待办全部完成，`pending` 归零
- 建立了 `sync` 作为真实入库的唯一权威进度指标
- 50 题 Golden 回归可以完整跑通，`unresolved = 0`

因此，**P8 不应继续以“数据有没有入库”为主线**。

P8 的核心问题已经变为：

> 在语料由 189 篇 / 9,780 chunk 扩张至 3,566 篇 / 296,385 chunk 后，如何稳定地将正确知识召回并排到前列，同时建立可持续扩容的检索质量评价体系。

---

## 0.2 当前最核心问题

当前生产配置 `hybrid_rerank`：

| 指标 | 当前 | 历史门线 |
|---|---:|---:|
| Hit@5 | 0.82 | 0.90 |
| MRR | 0.640 | 0.75 |
| NDCG | 0.678 | 0.80 |
| exact Hit@5 | 0.833 | 0.95 |
| semantic Hit@5 | 0.875 | 0.85 |

当前 `gate_pass = false`。

但失败的 9/50 道题中：

- `LOW_DENSE_RANK` × 5
- `NO_RECALL` × 2
- `BAD_FUSION` × 1
- `BEST_ARM_FAIL` × 1

这说明当前最主要的失效模式不是“数据不存在”或“索引缺失”，而是：

1. 正确内容已经进入候选集合，但排名被大量新增干扰项压低；
2. 候选池 / fusion / rerank 深度不足；
3. 部分题目存在真正的召回不足；
4. 混合不同价值密度、不同文档类型的语料后，单一全库排序开始暴露结构性问题。

---

## 0.3 P8 总体策略

P8 必须遵循如下顺序：

```text
冻结 P7 基线
    ↓
建立更可靠的 Benchmark
    ↓
做最小化参数实验
    ↓
对失败题做逐层归因
    ↓
判断瓶颈属于：
召回 / 融合 / 重排 / 语料竞争
    ↓
仅对证据支持的瓶颈做针对性改动
    ↓
设计 Corpus Routing / 分层检索
    ↓
重新标定正式生产 Gate
```

在上述步骤完成前：

**禁止直接升级 4B reranker。**  
**禁止全量重新分块。**  
**禁止全库重新 embedding。**  
**禁止修改 D 盘引擎代码。**  
**禁止因为旧门线未通过就直接降低 Gate。**

# 1. 事实、判断、建议的严格区分

后续窗口必须始终区分以下三类内容。

## 1.1 已确认事实

以下事实来自 P7 实测结果：

1. 当前索引数据完整性基本通过。
2. Golden 当前未达旧门线。
3. 历史 Golden 基线是在远小于当前规模的语料上建立。
4. 语料规模约扩大至历史基线的：
   - 文档数 18.9 倍；
   - chunk 数 30.3 倍。
5. 9 道失败题中，大多数并非“完全召回不到”。
6. 当前生产链路为：

```text
dense top-50
terms top-50
trigram top-30
    ↓
weighted RRF
    ↓
fused_k = 30
    ↓
rerank_k = 24
    ↓
final_k = 10
```

7. 当前 hybrid_rerank p95 约为 1,411 ms。
8. 现有 50 题 Golden 样本量较小。
9. 当前语料由多种性质明显不同的文档混合组成。
10. 引擎存在若干已确认的 silent failure / doc_id / roots / worker IPC 缺陷。

---

## 1.2 当前工作判断

以下内容是本阶段的工程判断，不应被后续窗口错误描述为已证实事实：

1. **旧门线不应直接废弃，但也不能继续被视为唯一正式生产门线。**
2. 当前检索退化是真实的，但部分退化来自语料规模变化造成的竞争增强。
3. `LOW_DENSE_RANK` 占多数意味着“候选深度 + 排序”应优先于“重建数据”。
4. 混库检索很可能是未来扩容后的结构性瓶颈之一。
5. 当前 0.6B reranker 尚不能被判定为能力不足。
6. 当前 chunk 方案尚不能被判定为根本问题。
7. 对 50 题进行大规模参数扫描存在显著过拟合风险。

---

## 1.3 建议性质内容

以下为 P8 建议：

- 扩展 Benchmark；
- 参数阶梯实验；
- 引入 candidate recall 指标；
- 做 query / source type 分型；
- 构建 corpus routing；
- 建立 Safe Indexing Gate；
- 重新标定 production gate。

这些建议必须通过实验结果逐步确认，而不是一次性全部实现。

# 5. P8-1：重构 Benchmark

## 5.1 为什么必须做

现有 50 题可以继续保留，但不适合承担：

- 调参集；
- 验收集；
- 长期 production gate；

三个角色。

否则调参过程会逐渐拟合这 50 题。

---

## 5.2 推荐结构

建立三层评测集。

### A. Legacy Golden

现有 50 题。

用途：

> 历史兼容 / Canary / Regression。

原则：

**永远冻结，不修改。**

---

### B. Development Benchmark

建议新增约 100～150 题。

用途：

- 参数实验；
- 失败归因；
- routing 设计。

允许随着 P8 早期发现问题进行有限修订，但所有修订必须有版本号。

---

### C. Holdout Benchmark

建议新增约 50～100 题。

用途：

> 最终验收。

在调参阶段不得查看逐题结果。

---

## 5.3 题目分型要求

新题集不能随机抽题。

至少覆盖：

| query_type | 说明 |
|---|---|
| exact_entity | 公司、产品、人物、指标 |
| exact_number | 数值、日期、比例 |
| semantic_thesis | 观点、逻辑、结论 |
| causal | 因果链条 |
| temporal | 某阶段发生了什么 |
| long_tail | 低频主题 |
| cross_doc | 多文档共同支持 |
| flagship | 深度报告知识 |
| daily | 日报 / 市场短评 |
| discussion | 即时讨论 |
| image_ocr | 来自配图 / OCR |
| bilingual | 中英混合或译文 |

---

## 5.4 每题必须包含的字段

推荐格式：

```json
{
  "id": "FB001",
  "query": "...",
  "query_type": "semantic_thesis",
  "target_doc_id": "...",
  "target_section_id": "...",
  "acceptable_docs": [],
  "source_type": "flagship",
  "difficulty": "medium",
  "temporal": false,
  "notes": "...",
  "split": "development"
}
```

---

## 5.5 不允许只标一个绝对答案

对于综合观点类问题，可能存在多个合理文档。

因此：

```text
target_section_id
```

之外建议支持：

```text
acceptable_docs
acceptable_sections
graded_relevance
```

避免把真正合理结果误判为失败。

# 7. P8-3：参数实验矩阵

## 7.1 原则

禁止直接大范围网格搜索。

原因：

- 样本量仍然有限；
- 参数之间高度耦合；
- 容易过拟合；
- 难以解释哪个参数真正生效。

---

## 7.2 第一轮实验

仅改变：

- `fused_k`
- `rerank_k`

保持：

```text
dense_k = 50
terms_k = 50
trigram_k = 30
```

实验：

| ID | fused_k | rerank_k |
|---|---:|---:|
| A0 | 30 | 24 |
| A1 | 40 | 32 |
| A2 | 50 | 40 |
| A3 | 60 | 50 |

重点回答：

> 已召回但掉出前 5 的 5 个 `LOW_DENSE_RANK` 是否改善？

---

## 7.3 第二轮实验

仅在第一轮仍存在明确 NO_RECALL 时执行。

| ID | dense_k | terms_k | fused_k | rerank_k |
|---|---:|---:|---:|---:|
| B0 | 50 | 50 | best_A | best_A |
| B1 | 75 | 75 | 50 | 40 |
| B2 | 100 | 100 | 50 | 40 |

重点回答：

> 两个 `NO_RECALL` 是否进入候选池？

## 7.4 第三轮实验

仅在 lexical / dense 明显存在偏置时执行。

# 9. 参数实验的停止规则

后续窗口不得无限调参。

满足以下任一条件即停止当前参数方向：

### 停止条件 1

连续两次扩大 K：

```text
Hit@5 提升 < 0.02
```

且：

```text
p95 增加 > 30%
```

则停止继续扩大候选池。

---

### 停止条件 2

Gold 已进入 reranker 输入，但始终无法上升至合理位置。

说明问题可能属于：

- reranker capacity；
- chunk 内容；
-语料同质干扰。

不得继续单纯扩大 K。

---

### 停止条件 3

candidate Recall 已接近饱和，例如：

```text
Recall@50 >= 0.95
```

但：

```text
Hit@5 仍显著低于目标
```

则转向排序问题。

# 11. P8-4：混库检索验证

## 11.1 当前问题

目前：

- 短篇日报；
- 讨论帖；
- 公众号；
- 交易台；
- 正式研报；
- 长篇旗舰研究；

在同一检索空间竞争。

这在知识库扩容后可能导致：

> 高频低深度语料压制低频高价值语料。

---

## 11.2 首先做实验，而不是直接改架构

先给所有文档增加或确认：

```text
source_type
corpus_tier
```

建议最小分类：

```text
flagship
formal_report
daily
discussion
image_material
other
```

---

## 11.3 做分层离线实验

对同一批 query 分别跑：

```text
ALL corpus
flagship only
formal_report only
daily/discussion only
```

比较：

```text
gold rank
Hit@5
candidate recall
```

如果 flagship query 在：

```text
flagship-only rank = 1~3
ALL rank = 10+
```

则可以比较明确判断：

> 存在 corpus competition。

# 12. P8-5：最小化 Corpus Routing

只有 P8-4 证明混库竞争显著后才执行。

## 12.1 第一版不要上 LLM Router

使用规则 + metadata。

例如：

```text
query
 ↓
简单 query type / source prior
 ↓
多 corpus 检索
```

---

## 12.2 推荐第一版

```text
Query
  ├─ flagship pool
  ├─ formal report pool
  └─ daily/discussion pool
        ↓
各自 Top K
        ↓
merge
        ↓
global rerank
```

---

## 12.3 推荐候选比例

例如：

```text
flagship       15
formal_report  25
daily          20
```

然后统一进入 reranker。

这只是实验值，不是最终配置。

---

## 12.4 为什么优先分池而不是直接加权

因为分池可以保证：

> 少量高价值 corpus 至少获得候选席位。

单一 global vector top-K 很容易被高频近义片段挤满。

# 14. Safe Indexing Gate

鉴于底层引擎存在多个已确认缺陷，P8 必须将现有 workaround 正式制度化。

---

## 14.1 Preflight Gate

每次索引之前检查：

```text
roots 与预期完全一致
↓
只读 scanner
↓
DELETED = 0
↓
doc_id collision scan
↓
Qdrant reachable
↓
SQLite reachable
↓
embedding provider ready
```

任一失败：

```text
ABORT
```

不得自动继续。

---

## 14.2 Apply Gate

索引过程中必须记录：

```text
batch_start
batch_end
indexed
failed
skipped
heartbeat
```

禁止以：

```text
process alive
chunks changed
```

作为进度。

---

## 14.3 Post-index Gate

必须检查：

```text
sync == expected
chunks == fts_terms
chunks == fts_trigram
chunks == qdrant_points
qdrant_gap == 0
```

---

## 14.4 Retrieval Smoke Gate

索引完成后：

运行固定小样本 Golden。

如显著退化：

```text
INDEX COMPLETE
但
RELEASE BLOCKED
```

不要混淆“索引成功”和“检索可发布”。

---

# 15. 底层引擎缺陷优先级

## P0-1：roots 导致跨语料误删

# 18. 是否接受 2 个 NO_RECALL

目前不能直接宣布“可接受”。

必须首先判断：

1. gold 是否确实存在；
2. gold chunk 是否信息完整；
3. query / gold 是否存在表达差异；
4. dense top100 是否能召回；
5. lexical 是否可召回；
6. 是否只有人工理解才能建立关联。

只有第 6 类才可以考虑：

```text
known hard case
```

而不是工程 bug。

---

# 19. 什么时候允许测试 4B reranker

只有同时满足：

```text
Candidate Recall 足够高
AND
gold 已稳定进入 rerank pool
AND
0.6B reranker 仍系统性将 gold 排低
```

才能开启：

```text
0.6B vs 4B
```

对照实验。

评估：

```text
Hit@5
MRR
NDCG
p95
VRAM
稳定性
```

如果质量收益很小但延迟大幅增加，不升级。

---

# 20. 什么时候允许重新分块

只有出现下列证据才允许：

- gold 所在 chunk 缺乏必要上下文；
- 多个相关 chunk 被切碎；
- heading / table / chart 信息丢失；
- candidate recall 因 chunk 语义不完整而失败。

否则：

**禁止重分块。**

因为重分块将导致：

- 296k chunk 全量重建；
- embedding 重算；
- Qdrant 重建；
- baseline 失效；
- 巨大回归成本。

# 28. 最终原则

本项目下一阶段的核心思想不是：

> “为了让 Golden 通过，不断调参数。”

而是：

> **建立一个能够证明“为什么检索成功 / 为什么检索失败”的系统。**

当知识库从数百篇扩展到数千篇、未来再扩展到上万篇时，最大的风险已经不是数据处理本身，而是：

> 正确知识仍然存在，但逐渐淹没在越来越多的相似内容中。

P8 的任务，就是在继续扩容之前解决这一问题。

只有当：

```text
数据完整性
+
召回可解释性
+
排序稳定性
+
语料分层治理
+
生产 Gate
```

全部建立后，项目才适合进入后续更复杂的 Research OS、Judgment、Topic、Agent 等上层能力开发。
