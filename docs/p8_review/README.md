## 1. 项目与本次评审目的

我们把 180K Research 知识星球语料（券商研报 / 日报 / 交易台 / 讨论帖 / 配图 OCR / 旗舰深度报告）加工为可检索知识库，交付形态是**引擎内的全量索引**（SQLite 目录库 + FTS + Qdrant 向量库）。

P7 已完成全量入库并建立一致性可核验的数据底座（四方计数一致 `consistent: true`）。**当前核心问题**：Golden 检索回归未过旧门线（`gate_pass = false`，Hit@5 0.82 vs 门线 0.90），需要外部评审就**瓶颈定性、优化路径、门线标定**给出独立意见。

语料从 **189 篇 / 9,780 chunk** 扩张到 **3,566 篇 / ~296,385 chunk（18.9× / 30.3×）**后，同一套 50 题、同一批金标未达标。

## 2. 核心结论（本评审包已完成的 P8 工作）

1. **瓶颈是「语料竞争」**：同一批 50 题，仅把检索域从全库 3,566 篇收窄到旗舰归档 187 篇，Hit@5 **0.82 → 0.90**、MRR 0.640 → 0.752、NDCG 0.678 → 0.789、NO_RECALL 2 → 0。（`metrics/corpus_competition.json`）
2. **候选深度/召回广度都不是瓶颈**：扩 fused_k/重排深度无收益且 p95 +79%（触发停止规则）；扩 dense/terms 到 100 把失败题拉进候选池但其融合名次 117/195，够不到重排。
3. **单参数杠杆最多 +0.02 Hit@5**；只有语料分层/隔离能到 0.90 ⇒ 架构性答案指向 **Corpus Routing（分层检索）**。
4. **语料层发现**：外资研报 tier 占全库 **74%** 的 chunk，其 **99.9% 落在占位标题下**（`元信息` 覆盖 155,616 chunks）——根因是**抽取阶段丢失标题**（抽样源 markdown 24,133 行仅 2 个 `#` 标题），不是引擎解析错误。
5. **引擎/流程缺陷**：backend reconcile 会非确定性地重解析 `M04/M09/_最终报告`（M09 在 45↔77 chunks 间跳），使旧金标间歇性解析失败、chunk 总数在 296,380↔296,385 抖动。

详见 `reports/P8_中期报告_WP1_WP2_20260911.md`。

## 4. 请评审重点回答

1. **定性**：Hit@5 0.82 / MRR 0.640 / NDCG 0.678 未过旧门线（0.90/0.75/0.80），应判为「检索质量回归（需调优）」还是「门线需随语料规模重标定」，抑或两者并行？
2. **路线**：在「单参数杠杆 ≤+0.02、隔离可到 0.90」的证据下，是否认可 **Corpus Routing / 分层检索** 是主杠杆？第一版规则+metadata 分池的候选比例如何设？
3. **门线**：旧 50 题转 Legacy Canary、由 Development + Holdout 重建正式门线的做法是否成立？样本量如何定？
4. **候选深度**：我们依据「扩 K 无收益、延迟大增」停止扩池，并认为瓶颈在排序/竞争——该判断是否成立？是否有遗漏的机制？
5. **语料治理**：外资研报 74% chunk 标题丢失，是否值得局部重抽取+重索引（代价大、触及重分块红线）？还是先以 metadata 分池 + 重排改进规避？
6. **重排**：残余失败（进池后排 5 名外）是否指向 0.6B reranker 能力上限？是否满足「上 4B 对照」的前置条件？
7. **工程缺陷**：跨批 doc_id 不消歧导致整批静默回滚、roots 语义导致跨语料误删、worker IPC 无超时、静默失败 exit 0、reconcile 非确定性重解析——优先级与修复建议？
