# 个人深度学习平台：产品需求 V1.0

日期：2026-09-05（Asia/Shanghai）  
状态：用户已明确产品目标；本文件为待实施需求，技术方案与验收阈值为开发建议。  
开发入口：[任务计划与验收](DEEP_LEARNING_PLATFORM_DEVELOPMENT_PLAN.md)。

## 1. 目标与优先级

用户明确的核心目标：持续补充 AI 分析报告，把各类知识建立有依据的联系，帮助发现潜在研究方向并提出选题，同时让没有历史对话的外部窗口准确理解研究方向、获得研究基础并接续研究。

这里的“深度学习”指个人持续理解、研究与知识积累，不指训练神经网络。

产品主线：

```text
长期研究方向 + 现有问题与判断
              ↓
新报告 → 研究增量 → 知识联系候选 → 主题研究地图
                                      ↓
                           缺口/冲突 → 候选选题
                                      ↓
                           用户选择 → 研究上下文包
                                      ↓
                           外部 Worker → 研究成果
                                      ↓
                           修订候选 → Preview / Human Apply
                                      ↓
                           更新主题状态 → 下一轮学习与研究
```

下一轮开发应优先完成一个真实主题的纵向闭环。基础运行可靠性属于支撑任务；检索调参、通用界面美化、新模型接入不得挤占该主线。用户后续明确的优先级调整优先。

本文件不代表批准自动执行研究、自动修改正式认知或批量处理全库，也不代表要求当前窗口实施代码。

## 2. 成功体验

用户打开一个主题，可以回答：

1. 我为什么研究它，与哪些长期方向有关？
2. 我目前理解到哪里，哪些判断已确认，哪些只是猜测？
3. 新报告贡献了什么，哪些只是重复表述？
4. 不同报告、概念、机制之间有什么联系，依据在哪里？
5. 哪个问题最值得继续研究，为什么现在值得做？
6. 把任务交给新窗口后，它能否准确接续，而不重新写一篇泛泛综述？
7. 成果返回后，原问题、判断和研究地图具体发生了什么变化？

北极星指标：重要问题的有效推进，以及已有知识在后续研究中的可追溯复用。报告数量、节点数量、生成选题数量均不是独立成功标准。

## 3. 当前基础与差距

基准：2026-09-05 阅读 GitHub main 与本地对应源码；远端包含 2026-09-03 的 External Worker Launcher 和 Task Center 调整。本轮没有完成真实 UI、外部 Worker 或无模型环境验收。后续开发须重新核对当前代码，不能把本表当作永久状态。

|---|---|---|
| 材料与证据 | Parser、Chunker、全文/向量检索、Evidence Basket、上下文扩展 | 新报告相对主题当前状态的增量识别 |

## 4. 首版范围

### 必须交付

- 一个可选择的试点主题及用户确认的研究方向。
- 主题研究档案：方向、问题、判断、证据、联系、缺口、候选选题。
- 新报告的增量分析与有来源的联系候选。
- 少量可解释、去重、可拒绝或延后的选题卡。
- 从选题到研究上下文包，再到现有 TaskPack 的交接链。
- 外部成果返回后的问题推进与判断修订候选。
- 候选、正式认知和历史版本的清晰区分。
- 本地基础读取、全文检索和打包不依赖模型/向量服务正常工作。

### 后续增强

- 多主题机制迁移与跨主题方向发现。
- 研究失败记录、知识复用统计、长期未解决问题回访。
- 用户自述理解、反例和迁移问题；反馈只作提示，不自动评分为“已掌握”。
- 根据真实使用数据改善选题排序；探索性选题单独说明理由。

### 首版不做

- 全库自动建图、批量自动研究、无限递归生成选题。
- 自建大模型服务、新增模型供应商 SDK、自动训练推荐器。
- 先做复杂图谱可视化或另建独立前端产品。
- 自动提升 AI 结论为个人正式认知，自动撤回旧判断。
- 从点击行为暗中改变用户长期研究方向。
- 扩展任意文件格式采集链；首版复用现有报告输入能力。

## 5. 用户流程与功能要求

### FR-01：研究方向与主题研究档案

长期方向记录：关注原因、核心问题、纳入/排除范围、研究偏好、当前优先级。方向由用户明确设定；AI 只能建议调整。

主题页至少包含：当前理解、关键问题、关键机制、支持/反对证据、最近变化、下一步选题。主题摘要必须可以定位到组成它的正式对象和候选材料，展示更新时间与来源版本；过期时明确标记，不冒充当前状态。

新用户可以手工建立一个问题与初步判断，不要求先生成 AI 报告。未确认内容保留为草稿。

### FR-02：报告增量

用户选择已索引报告及目标主题，发起一次显式分析。自动化仅指一次授权任务内部的分析与候选生成；首版不默认后台调用外部 AI。

每项结果分类为：新增认识、补充证据、潜在冲突、适用条件变化、重复内容、无法判断。

结果应关联报告片段与受影响的问题/判断，并说明差异理由。新入库时间不等于信息新鲜度；保留原材料日期、分析时间及不明日期状态。报告过长或证据不足时报告覆盖范围，不声称完整分析。

### FR-03：有依据的知识联系

关系类型：主题相关、概念依赖、机制假设、支持、反对、条件限制、类比启发。

每条关系保存两端对象、关系类型、解释、证据定位、适用范围、提出者、审核状态。区分“资料作者主张”“AI 推测”“用户确认”。共现与相似不能自动转为因果。

AI 联系进入候选层；接受/拒绝/延后均可记录理由。拒绝不修改原始材料。相关性去重不能误合并不同时间或不同条件下的判断；疑似相同只提示。

### FR-04：缺口与选题

候选触发来源：结论冲突、机制中断、重要前提未验证、适用条件变化、跨领域类比、长期问题停滞。

选题卡必填：

- 标题、所属主题、触发类型、关联问题/判断/证据。
- 为什么值得研究、相对已有成果的预计增量。
- 当前已知与未知；至少列出可比较的解释，或明确是探索性问题。
- 能区分解释的证据/观察；证据可得性和局限。
- 研究范围、排除内容、建议方法、交付要求。
- 重复研究检查结果、预估工作量档位及理由。
- 推荐优先级及理由、候选状态、生成时间。

“预计增量”和“优先级”均是建议，不写成确定收益。首版采用可读理由，不使用未经校准的精确评分。

候选状态建议：proposed → selected / deferred / rejected / superseded。是否已启动或完成通过关联 TaskPack 状态读取，不另建相互冲突的研究执行状态机。重复提交同一选题不重复创建任务。

每次默认生成不超过 5 个候选（建议产品默认值，可配置）；不足时如实少给，允许零候选，禁止为了凑数生成题目。探索性题目明确标识。

### FR-05：研究上下文包

必须分三层输出：长期方向、主题当前状态、本次任务。外部窗口无需访问本地绝对路径或历史对话即可理解研究基础。

包内语义文件建议（待 DL-00 确认协议，不表示已经存在）：

| 内容 | 建议表达 |
|---|---|
| 人可读总入口 | `research_brief.md`：研究目的、范围、当前认识、缺口、验收 |
| 结构化上下文 | `research_context.json`：方向/主题/问题/判断的稳定 ID 和版本 |
| 现有输入 | 继续使用 TaskPack evidence 与 Cognition context，不复制另一套权威正文 |
| 输出指令 | 扩展现有 Worker instruction，要求说明新证据、差异与未解决事项 |

每个重要“已知”附来源，保留反方材料和不确定性。明确本次能否检索外部资料；现有仅使用包内材料的 Worker 指令不能与“联网补证”任务暗中冲突。需联网的任务在能力未提供前应显示阻塞，或明确转为包内分析。

上下文有体量预算；超限时分层选择或拆任务，展示遗漏部分。不得静默丢弃反证或把片段截取说成全文。

导出前展示内容清单，排除凭据、行为日志、无关私人记录。记录来源对象版本与生成时间；导出后内容作为本次研究快照保留，不随主题更新而悄悄改变。

### FR-06：成果回流与认知变化

外部成果必须说明：回答了哪个问题、相对既有认识改变了什么、哪些证据支持变化、哪些仍未知。

支持以下候选意图：新建判断、补充证据、修订判断、建议撤回或取代、推进问题、增加联系。每项指向已有对象或解释为何新建；保留旧表述、新表述和变化理由。

KE 只创建 staging candidate，正式执行仍由 Cognition Preview / Human Apply 负责。真实 Cognition 缺少某种候选/预览能力时，只支持可表达的子集并标明限制，不能绕过正式写入边界。

成果生成后若目标判断已更新，应显示冲突并重新预览；用户拒绝候选后正式知识不变。正式确认后读取并验证实际对象，再更新派生主题状态。发送成功不能等同正式写入成功。

### FR-07：学习与复用

主题页保留“我的解释”“哪些条件下不成立”“下一个检验案例”等轻量草稿入口。个人解释不自动被 AI 替换。

后续显示证据/判断被哪些研究复用，以及研究解决了什么问题。检索“有用”、用户赞同、证据可靠性分别表达。

## 6. 逻辑对象与存储职责

以下为待映射的逻辑模型，不是新增数据库或已存在 API 的承诺：

| 对象 | 最小字段 | 权威归属 |
|---|---|---|
| ResearchDirection | id、目标、范围、优先级、版本、确认状态 | 用户确认内容经 Cognition 管理；AI 调整建议在 KE 候选层 |
| TopicResearchState | topic_id、问题/判断引用、摘要、来源版本、更新时间 | KE 可重建派生视图；正式 Topic 仍在 Cognition |
| Question / Judgment | 稳定 ID、表述、状态、主题、版本 | 复用 Cognition，不另建正式主库 |
| Concept / Mechanism | 定义或机制、条件、引用、审核状态 | 优先映射现有 Cognition；不适配时先提出契约扩展 |
| KnowledgeRelation | 两端 ID、类型、理由、证据、范围、审核状态 | KE 存候选；正式关系由 Cognition 统一管理 |
| ReportDelta | report_id、topic_id、分类、对象引用、片段引用、理由 | KE 候选/派生数据 |
| ResearchOpportunity | 选题卡字段、状态、关联任务、拒绝理由 | KE 研究规划元数据，不冒充正式判断 |
| ResearchContextSnapshot | 版本、方向/主题/对象引用、范围、遗漏、时间 | TaskPack 持久快照 |
| ResearchOutcomeLink | task_id、原问题、候选引用、正式结果引用 | KE 记录关联；正式对象从 Cognition 读取 |

稳定 ID 用于关系端点；标题和文件路径变化不得导致知识联系失联。候选存储、恢复和备份纳入现有 runtime 体系，落地位置由 DL-00 决定。禁止将 durable 研究状态只放在浏览器 localStorage。

## 7. 架构边界与兼容性

- Cognition App：正式认知与产品主入口；所有正式变化由它执行。
- Knowledge Engine：材料、证据、检索、TaskPack、候选规划和派生视图。
- External Worker：语义分析与研究执行，不成为正式事实来源。
- SQLite/向量派生索引继续分离，允许界面联邦展示，不混用评分空间。
- 基础浏览、全文检索、读写研究规划元数据和打包走本地确定性路径。
- 关系建议、报告增量分析、选题论证需要语义分析时，显式调用外部 Worker；没有该能力时展示手工路径或不可用原因，不伪造自动能力。
- 新 TaskPack 字段须版本化并保留旧包读取；旧 Worker 无法处理新任务时显式拒绝或降为受支持类型，不假装执行成功。
- 搜索/排序反馈不自动变成认识、不自动修改排序参数。

用户目标已确定；对象归属映射、新契约版本、UI 承载页等仍需在真实代码中核对。当前文档不能代替实现前的契约检查。

## 8. 端到端验收场景

试点主题由用户选择；“AI 基础设施约束与企业收益兑现”仅为可替换示例，不代表用户已确认长期方向。

建议小样本包含：5—10 份真实报告、至少 3 个已有判断、2 个未解决问题、一组冲突材料、一份重复报告。数字是首轮验收建议，不是当前数据统计。

验收过程：

1. 建立主题档案并确认当前研究方向。
2. 选择一份新报告，生成可定位来源的增量与联系候选。
3. 识别一个真实缺口，提出有研究价值且不重复的选题。
4. 用户选择后，导出完整上下文包并生成关联 TaskPack。
5. 新窗口只读取包，正确复述目的、已有认识、缺口、边界与交付要求。
6. Worker 完成一次研究，结果形成针对已有对象的变化候选。
7. 在真实 Cognition UI 预览并人工确认其中一项；验证正式对象和旧版本记录。
8. 从更新后的主题再次创建任务，能够带入新认识并解释变更原因。

只读演示、模拟 Worker、接口返回成功均不能替代第 5—8 步的真实闭环。任何未执行环节保留 NOT VERIFIED。

## 9. 评价与停止条件

机械验收：引用可定位、关系类型有效、旧任务可读、拒绝不改变正式对象、重试不重复创建、基础路径无模型可用。

人工验收：联系是否成立、选题是否值得、上下文是否准确表达研究方向、回流是否推进认识。由用户或指定审阅者给出 PASS / CONDITIONAL / FAIL 及理由，模型自评不替代。

观察指标：被采纳且理由明确的选题、重复选题、无依据关系、任务上下文误解、实际问题推进、旧知识复用、完整闭环所需操作。先记录基线，不预设增长收益或准确率承诺。

如果多数联系无依据、候选题重复、外部窗口仍需大量口头补充、成果只能新建条目而不能推进原问题，应停止扩库与批量执行，先修复闭环。
